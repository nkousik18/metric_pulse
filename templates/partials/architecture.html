How it's built

A local-first pipeline: the Olist CSVs load into DuckDB, dbt models them, Python detects, decomposes and narrates each day, and three LangGraph agents work on top. A Django API serves this page. The original AWS deployment (S3, Redshift, Lambda, SNS) was retired in November 2026; its code is kept and can be switched back on.

The pipeline

  1. Olist CSVs 7 tables, 2016–2018 (CC BY-NC-SA 4.0)
  2. DuckDB local warehouse, loaded by ingestion.load_local
  3. dbt staging → marts → daily metrics by segment
  4. Detection z-score per day, plus a data-freshness check Onboarding agent brings new datasets in here
  5. Decomposition each segment's share of the change, by region, product, payment
  6. Narrative a templated explanation, no LLM Investigation agent explains with cited numbers
  7. Alert a Markdown file in the local outbox Action agent proposes a response for approval

Stages pass plain dictionaries, and every step catches its own errors so one failure never takes down the run. The agents use Groq's gpt-oss-20b and gpt-oss-120b, traced in LangSmith.

How the agents are measured

Each eval replays real cases and appends one row to a committed ledger (evals/ledger.jsonl): the commit, the models, the prompt hash and every metric with its numerator and denominator. The expected answers were labelled by hand: 28 days for detection, an investigation golden set, the Superstore classification for onboarding, and 15 golden cases plus 10 prompt-injection attempts and safety probes for the Action Agent. python -m observability.drift reruns them all and lists any metric that fell below its accepted baseline.
